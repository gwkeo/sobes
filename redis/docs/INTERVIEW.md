# Redis: шпаргалка к собеседованию

Это дополнение к проекту `redis-catalog`. Здесь — не пересказ документации, а
ответы, которые полезно уметь давать голосом, с привязкой к коду проекта.

---

## 1. Как рассказать про проект за 2 минуты

> У меня есть сервис каталога на Go. Redis там используется как L2-кэш перед БД,
> плюс для распределённых блокировок, rate limiting и идемпотентности.
>
> Чтение идёт через cache-aside: сначала локальный L1 с TTL в пару секунд, потом
> Redis. В Redis лежит не голое значение, а конверт с `fresh_until` и
> `stale_until`, поэтому работает stale-while-revalidate: просроченное значение
> можно отдать сразу и обновить в фоне.
>
> От stampede защищают singleflight внутри инстанса и `SET NX PX` + Lua-release
> между инстансами. От cache penetration — negative caching с коротким TTL.
> TTL рандомизирован, чтобы ключи не протухали одновременно.
>
> Инвалидация: после коммита в БД удаляю ключ товара, инкременчу версию списков
> (она входит в ключ, поэтому не нужен `SCAN`) и публикую событие в Pub/Sub,
> чтобы другие инстансы сбросили L1. Есть double delete как страховка от гонки.
>
> Rate limit — sliding window на ZSET через Lua. Идемпотентность POST —
> `Idempotency-Key`, response сохраняется в Redis, завершение атомарное через Lua,
> чтобы старый владелец lock не перезаписал новый ответ.
>
> Если Redis падает, сервис не падает: ошибки кэша логируются, запрос идёт в БД,
> readiness показывает degraded. Это осознанный trade-off: кэш опциональный.
>
> В тестах на miniredis проверены 50 параллельных промахов → один запрос в БД,
> SWR, истечение negative-записи, 409/422 в идемпотентности и деградация без Redis.

Дальше интервьюер обычно копает в одну из тем ниже.

## 2. База

### Почему Redis быстрый?

- Данные в памяти, нет дискового I/O на чтение.
- Простые структуры данных с предсказуемой сложностью (`O(1)`/`O(log N)`).
- Один поток исполняет команды, поэтому нет блокировок на каждую операцию и
  гонок между командами; сетевой I/O может быть многопоточным (Redis 6+).
- Event loop на `epoll`/`kqueue`, эффективная обработка многих соединений.
- Протокол RESP компактный и простой.

Важно: «single-threaded» не значит, что любая команда быстрая. `KEYS`, большие
`SMEMBERS`, тяжёлый Lua или `DEL` огромного ключа могут заблокировать сервер.
Для удаления больших объектов есть `UNLINK`.

### Какие структуры данных и где их применять?

| Структура | Типичные задачи | В проекте |
|---|---|---|
| String | кэш JSON, счётчики, locks, idempotency | значения кэша, `INCR listver`, lock |
| Hash | объекты с полями, частичное обновление | не используется (можно хранить товар) |
| List | очереди, recent items, `LPUSH`/`BRPOP` | нет |
| Set | уникальные значения, теги, пересечения | нет |
| Sorted Set | лидерборды, rate limit, delayed queue | sliding window, `ZREMRANGEBYSCORE` |
| Stream | event log, consumer groups | альтернатива Pub/Sub для надёжности |
| Bitmap | DAU, флаги | нет |
| HyperLogLog | приблизительный unique count | нет |

### TTL: как Redis удаляет ключи?

Два механизма:

1. **Пассивно** — при обращении к ключу проверяется, не истёк ли он.
2. **Активно** — периодически Redis сэмплирует ключи с TTL и удаляет истёкшие.

Из-за этого «истёкший» ключ может ещё занимать память. На репликах ключи не
удаляются независимо: primary инициирует удаление и реплицирует его.

`TTL` возвращает `-1` (нет TTL) или `-2` (ключа нет). В коде не путать с
`redis.Nil` от `GET`.

### Eviction: что будет при `maxmemory`?

Политики: `noeviction`, `allkeys-lru`, `volatile-lru`, `allkeys-lfu`,
`volatile-lfu`, `allkeys-random`, `volatile-random`, `volatile-ttl`.

- `noeviction` — запись начинает падать с `OOM command not allowed`.
- `volatile-*` — вытесняют только ключи с TTL.
- LRU в Redis приблизительный (sampling), не точный.
- Для чистого кэша обычно `allkeys-lru`/`allkeys-lfu`, для данных — `noeviction`
  и отдельный инстанс.

В проекте compose использует `allkeys-lru` и `maxmemory 256mb`. Важный нюанс:
`listver` — не кэш, его потеря может привести к временной выдаче старых списков.
В проде такие служебные ключи лучше держать отдельно или использовать
`volatile-lru`.

### Persistence: RDB vs AOF

- **RDB** — снапшот через fork + copy-on-write. Компактно, быстро
  восстанавливается, но можно потерять данные между снапшотами.
- **AOF** — лог команд. `appendfsync always|everysec|no`. `everysec` — разумный
  компромисс, теряется до секунды.
- **Гибридный режим** (RDB + AOF) в Redis 7 — часто лучший вариант.
- Для чистого кэша persistence можно вообще отключить.

### Репликация, Sentinel, Cluster

- **Репликация** асинхронная по умолчанию. `WAIT` позволяет дождаться
  подтверждения от реплик, но не даёт строгой консистентности.
- **Sentinel** — мониторинг, автоматический failover, клиент узнаёт новый master.
- **Cluster** — шардирование по 16384 слотам, `MOVED`/`ASK`, минимум 3 мастера.
  Мультиключевые команды и Lua должны работать с ключами в одном слоте.
  Hash tags `{user:42}:a` и `{user:42}:b` помогают.
- В Cluster обычный Pub/Sub broadcast идёт на все узлы; есть sharded Pub/Sub (7.0).

## 3. Кэширование

### Cache-aside vs read-through vs write-through vs write-behind

- **Cache-aside** (ленивый): приложение сначала читает кэш, при промахе — БД и
  запись в кэш. Самый распространённый. Так сделано здесь.
- **Read-through**: кэш сам загружает из БД при промахе (нужна интеграция).
- **Write-through**: пишем в кэш и БД синхронно. Кэш всегда свежий, но запись
  дороже и есть риск, что кэш забит тем, что не читают.
- **Write-behind**: пишем в кэш, а в БД асинхронно. Быстро, но можно потерять
  данные.

### Три классические проблемы

1. **Cache penetration** — запросы несуществующих ключей всегда идут в БД.
   Решения: negative caching, bloom filter, валидация ID.
2. **Cache stampede / thundering herd** — много параллельных промахов по одному
   ключу. Решения: singleflight, distributed lock, SWR, early refresh, jitter.
3. **Cache avalanche** — много ключей истекли одновременно (или Redis лёг).
   Решения: jitter, постепенный прогрев, circuit breaker, несколько инстансов,
   деградация в БД.

### Hot key

Один ключ читают на порядок чаще остальных. Решения:

- L1 в приложении (как здесь);
- реплики на чтение;
- разбиение ключа на `key:0..N` с рандомным выбором (осторожно с инвалидацией);
- локальный батчинг/агрегация;
- в Cluster — hot slot: ключ с hash tag может перегрузить один шард.

### Big key

Большой объект (сотни КБ/МБ, миллионы элементов) увеличивает latency, трафик и
время fork. Решения: сжать, разбить на части, хранить только нужные поля,
`UNLINK` вместо `DEL`, не делать `HGETALL` целиком.

### Что кэшировать и на сколько?

- Кэшировать имеет смысл дорогие чтения с высоким hit ratio.
- TTL — компромисс между свежестью и нагрузкой на БД.
- Для данных, где недопустима stale-выдача, кэш либо не используют, либо
  инвалидируют синхронно/через версии.
- Не кэшировать персонализированные ответы под общим ключом.

## 4. Инвалидация и консистентность

### Почему `DEL`, а не `SET` после обновления?

Классическая гонка cache-aside:

1. Читатель A промахнулся и прочитал старое значение из БД.
2. Писатель B обновил БД и сделал `SET` нового значения.
3. A записал своё старое значение в кэш — кэш «залип» на старом.

С `DEL` шаг 2 удаляет ключ, а шаг 3 может положить старое значение, но
следующий читатель увидит его только до TTL. Полностью проблема не решается,
поэтому добавляют double delete, версии, CDC/outbox.

### Double delete

После обновления: `DEL` → через небольшой интервал ещё `DEL`. Второй удаляет
значение, которое конкурентный читатель мог записать между коммитом и первым
`DEL`. Это эвристика, а не доказательство корректности.

### Версионирование ключей

Два варианта:

- версия в имени ключа (`list:{version}:...`), при изменении `INCR` версии;
- версия внутри значения + проверка при записи.

Плюс: не нужно удалять по шаблону. Минус: старые ключи живут до TTL, занимают
память; нужен разумный TTL.

### Как инвалидировать несколько инстансов?

- **Pub/Sub** — просто, но fire-and-forget, без гарантий доставки.
- **Redis Streams + consumer groups** — надёжнее, at-least-once, нужна
  идемпотентная обработка.
- **Keyspace notifications** — можно, но нужно включать в конфиге, события не
  гарантируют доставку и могут приходить после команды; для бизнес-событий
  обычно не лучший выбор.
- **Outbox/CDC** — самое надёжное: событие фиксируется в БД вместе с изменением.

Для L1 с коротким TTL потеря сообщения не критична: через пару секунд локальный
кэш сам истечёт. Это важное проектное решение.

## 5. Атомарность: pipeline, MULTI, Lua

### Pipeline

Не атомарен. Уменьшает RTT, отправляя несколько команд пачкой. Другие клиенты
могут выполнить свои команды между вашими.

### MULTI/EXEC

Команды выполняются атомарно, но **без rollback**: если одна упадёт во время
выполнения, остальные всё равно выполнятся. Ошибки постановки в очередь
(например, неверное число аргументов) отменяют транзакцию.

`WATCH` + `MULTI` даёт оптимистичную блокировку: если ключ изменился, `EXEC`
вернёт `nil`, и операцию нужно повторить. В go-redis — `Watch`/`TxPipelined`.

### Lua

Скрипт выполняется атомарно и блокирует сервер на время выполнения. Поэтому:

- никаких долгих циклов и сетевых вызовов;
- ключи передавать через `KEYS`, данные — через `ARGV`;
- в Cluster все ключи должны быть в одном слоте (hash tags);
- `redis.Script` кэширует SHA и сам делает fallback `EVALSHA` → `EVAL` при
  `NOSCRIPT`.

В проекте Lua используется для:

- снятия lock только своим token;
- sliding window rate limit;
- атомарного сохранения идемпотентного ответа.

## 6. Распределённые блокировки

### Правильный минимум

```text
SET lock:key <token> NX PX 30000
```

- `NX` — только если ключа нет;
- `PX` — чтобы lock не остался навсегда при падении процесса;
- `token` — случайный, чтобы снять только свой lock.

Снятие:

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
end
return 0
```

### Почему не `SET` + `DEL` без проверки?

Если lock истёк и его уже взял другой процесс, `DEL` удалит чужой lock. Тогда
два процесса могут одновременно считать, что владеют им.

### Гарантирует ли lock корректность?

Нет. Процесс может остановиться (GC, сеть), lock истечёт, а работа продолжится.
Для критичных операций нужны **fencing tokens**: монотонный номер передаётся в
хранилище, и хранилище отвергает операции со старым номером. Либо используют
оптимистичные версии/транзакции в БД.

Redlock (алгоритм с несколькими независимыми Redis) критикуют за то, что он не
даёт строгих гарантий при остановках процессов и часовых сдвигах. Для кэша и
оптимизации — ок; для денег — нет.

В проекте lock нужен только чтобы не дублировать загрузку кэша. Если он сломается,
будет лишний запрос в БД, но не потеря данных.

## 7. Rate limiting

### Алгоритмы

| Алгоритм | Плюсы | Минусы |
|---|---|---|
| Fixed window (`INCR`+`EXPIRE`) | простой, O(1) | burst на границе окна |
| Sliding window log (`ZSET`) | точный | память O(limit) |
| Sliding window counter | компромисс | приблизительный |
| Token bucket | средний rate + burst | нужен аккуратный Lua |
| GCRA | компактный, точный | сложнее объяснять |

### Почему Lua?

Проверка и запись должны быть атомарными. Иначе два инстанса одновременно
увидят «осталось 1» и оба пропустят запрос. Lua или `MULTI` решают это.

### Что делать при недоступном Redis?

- **fail-open** — пропускаем запросы, доступность важнее (выбрано здесь);
- **fail-closed** — 503, безопасность важнее;
- локальный fallback (token bucket в памяти) — компромисс.

Политику нужно выбирать по сценарию. Для антифрода/платежей — fail-closed,
для публичного API — часто fail-open с метрикой.

## 8. Идемпотентность

Идея: клиент присылает `Idempotency-Key`; сервер гарантирует, что повтор с тем же
ключом и тем же запросом вернёт тот же результат, а не выполнит операцию снова.

Что нужно:

- хранить ключ + fingerprint запроса (method, path, body hash);
- хранить статус, заголовки и тело ответа;
- различать «выполняется» и «готово»;
- TTL (обычно 24 часа);
- атомарно проверять владение lock при завершении;
- при повторном запросе с другим body — `422`.

Ограничение: если процесс упал после side effect, но до сохранения ответа, повтор
может создать дубль. Поэтому в БД нужен уникальный индекс/транзакция, а Redis —
вспомогательный слой.

В проекте `Complete` делает Lua-скрипт: проверяет token, сохраняет ответ и
удаляет lock одной операцией. Ключи `resp` и `lock` имеют общий hash tag, чтобы
работать в Redis Cluster.

## 9. Pub/Sub vs Streams vs keyspace notifications

### Pub/Sub

- at-most-once, без сохранения;
- подписчик, которого не было в момент публикации, сообщение не получит;
- нет ack и повторной доставки;
- отлично для invalidation, где потеря допустима.

### Streams

- append-only log, сохраняется;
- consumer groups, `XACK`, `XPENDING`, `XAUTOCLAIM`;
- at-least-once, нужна идемпотентная обработка;
- подходит для очередей, event sourcing, надёжной инвалидации.

### Keyspace notifications

- включаются `notify-keyspace-events`;
- событие публикуется после выполнения команды;
- не гарантируют доставку, не заменяют бизнес-события;
- можно случайно получить шторм событий и утечку паттернов.

## 10. Go и go-redis: частые грабли

1. **`redis.Nil`** — это не ошибка, а «ключа нет». Проверять через
   `errors.Is(err, redis.Nil)`.
2. **Контекст** — всегда передавать `ctx` из запроса; не `context.Background()`
   в handler'ах.
3. **Таймауты** — `DialTimeout`, `ReadTimeout`, `WriteTimeout`, плюс
   `context.WithTimeout` на операцию. Иначе упавший Redis подвесит запросы.
4. **Пул соединений** — `PoolSize`, `MinIdleConns`, `PoolTimeout`. При высоком
   concurrency маленький пул становится бутылочным горлышком.
5. **Ретраи** — `MaxRetries` может повторять неидемпотентные команды. Для
   `INCR`/`SET NX` это особенно опасно; понимать, что клиент ретраит.
6. **Pipeline** — `Pipeline()`/`Pipelined()` уменьшает RTT, но не даёт
   атомарности. Для транзакций — `TxPipelined`/`Watch`.
7. **Lua** — использовать `redis.NewScript`, а не собирать строки с
   пользовательскими данными.
8. **Ключи** — не `KEYS *` в проде; `SCAN` с `COUNT` и обработкой дублей.
9. **Сериализация** — JSON удобен, но дороже msgpack/protobuf. Для больших
   значений смотреть на сжатие и размер.
10. **Закрытие** — `defer rdb.Close()`, иначе утечка соединений.
11. **Pub/Sub** — `Channel()`/`ReceiveMessage` нужно закрывать; при реконнекте
    возможны пропуски.
12. **Ошибки** — не логировать пароли/ключи; в ключах не хранить PII.

## 11. Эксплуатация и метрики

### Что смотреть в `INFO`

- `INFO stats`: `instantaneous_ops_per_sec`, `keyspace_hits`, `keyspace_misses`,
  `evicted_keys`, `rejected_connections`.
- `INFO memory`: `used_memory`, `used_memory_rss`, `mem_fragmentation_ratio`.
- `INFO clients`: `connected_clients`, `blocked_clients`.
- `INFO replication`: роль, lag, `master_link_status`.
- `INFO keyspace`: количество ключей и TTL.

Hit ratio = `keyspace_hits / (keyspace_hits + keyspace_misses)`. Но он не говорит,
какие именно ключи промахиваются; нужны метрики по слоям/типам, как в проекте.

### Диагностика

- `SLOWLOG GET 10` — медленные команды (порог `slowlog-log-slower-than`).
- `LATENCY DOCTOR` / `LATENCY HISTORY`.
- `redis-cli --bigkeys` — большие ключи.
- `redis-cli --hotkeys` — горячие ключи (нужен LFU).
- `MEMORY USAGE key`.
- `CLIENT LIST`, `CLIENT NO-EVICT ON` (для важных соединений).
- `MONITOR` — только в отладке, сильно нагружает.
- `SCAN` вместо `KEYS`.

### Алерты, которые обычно нужны

- рост latency p99;
- падение hit ratio;
- `evicted_keys > 0` (если не ожидается);
- `rejected_connections`;
- ошибки команд у клиента;
- память > 80%;
- репликация отстаёт;
- master недоступен / failover.

## 12. Быстрые вопросы-ответы

**Redis — это база данных?**
Это in-memory key-value store; может быть и кэшем, и хранилищем, и брокером
сообщений. Выбор persistence/репликации определяет, насколько он «база».

**Почему нельзя `KEYS *`?**
Команда сканирует всё пространство ключей и блокирует event loop. На больших
инстансах — секунды/минуты. Используйте `SCAN`.

**`DEL` и `UNLINK`?**
`DEL` освобождает память синхронно, `UNLINK` — в фоне. Для больших ключей
`UNLINK` предпочтительнее.

**Чем `SET NX` отличается от `SETNX`?**
`SET NX` — современная команда с опциями `PX`, `EX`, `GET`; `SETNX` — старая,
без TTL. Используйте `SET ... NX PX ...`.

**Как сделать счётчик с TTL?**
`INCR key` + `EXPIRE key` — двумя командами; атомарно через Lua или `MULTI`.
Либо `SET key 0 EX ttl NX` при создании.

**Чем Pipeline отличается от транзакции?**
Pipeline — только батчинг по сети, не атомарен. `MULTI/EXEC` — атомарное
выполнение (без rollback).

**Можно ли откатить транзакцию в Redis?**
Нет. `MULTI/EXEC` не делает rollback; ошибки выполнения не отменяют остальные
команды. Нужна логика компенсации.

**Что такое cache stampede?**
Массовые одновременные промахи по одному ключу → лавина запросов в БД.
Лечится singleflight/lock/SWR.

**Что такое cache penetration?**
Поток запросов несуществующих ключей, который всегда идёт в БД. Лечится
negative cache/bloom filter.

**Что такое cache avalanche?**
Одновременное истечение большого числа ключей или падение Redis. Лечится
jitter, прогревом, circuit breaker, репликами.

**Почему TTL с jitter?**
Чтобы ключи, загруженные одновременно, не истекли в одну секунду.

**Почему `DEL`, а не `SET` после записи?**
`SET` может проиграть гонку и оставить старое значение; `DEL` безопаснее.
Полностью проблема решается версиями/CDC.

**Нужен ли distributed lock для кэша?**
Для корректности — нет, для оптимизации — да. Если lock сломается, будет лишний
запрос в БД.

**Как снять lock безопасно?**
Проверить token в Lua и только потом `DEL`.

**Что такое fencing token?**
Монотонный номер операции, который хранилище проверяет, чтобы отвергнуть
запись от «просроченного» владельца lock.

**Чем Pub/Sub лучше Streams?**
Проще и быстрее; но не гарантирует доставку. Streams — когда нужна надёжность.

**Как инвалидировать кэш на всех инстансах?**
Pub/Sub/Streams + короткий TTL L1. Либо версия ключа, которую видят все.

**Как избежать hot key?**
L1, реплики, шардирование ключа, батчинг; в Cluster — следить за hot slot.

**Что будет, если Redis недоступен?**
Зависит от политики: fail-open (идём в БД), fail-closed (503), локальный
fallback. В проекте — fail-open для кэша и degraded readiness.

**Как масштабировать Redis?**
Вертикально, read replicas, Cluster (шардирование), Sentinel (HA). Помнить про
мультиключевые операции и hot slots.

**Как понять, что кэш работает?**
Hit ratio, latency p99, нагрузка на БД, `keyspace_hits/misses`, метрики по слоям.
Но hit ratio 99% может быть бесполезным, если кэшируются дешёвые запросы.

**Что хранить в ключе?**
Namespace, версию, тип, ID. Не хранить PII/секреты в открытом виде; ограничивать
длину.

**Как тестировать Redis-код?**
`miniredis` для юнитов, реальный Redis в Docker/Testcontainers для интеграции,
`-race`, тесты на отказ (закрыть Redis, таймауты, reconnect).
