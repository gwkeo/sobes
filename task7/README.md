# Task 7 — Kafka в Go: практикум с продакшен-подходом

Цель — понять не только API Kafka, но и то, что происходит между приложением,
брокерами и consumer group: где хранятся записи, что означают подтверждения,
почему сообщения повторяются и как система ведёт себя при сбоях.

Это учебный стенд и серия небольших упражнений, а не попытка построить ещё один
сервис «на всякий случай». Код и объяснение каждой главы я даю в чате; ты
повторяешь у себя. После главы ты присылаешь короткий конспект, я проверяю его,
уточняю спорные места и только потом переходим дальше. Этот README — карта пути;
код заранее сюда не складываем.

## Сквозной сценарий

Разбираем отправку уведомлений. Сначала будет один topic с запросами на
отправку; дополнительные topics добавим, когда появятся отдельные причины для
них — результаты доставки и сообщения, которые не удалось обработать.

```text
API / producer ── notifications.requested.v1 ──► Delivery worker ──► provider
                                                   │
                                                   ├──► notifications.delivery.v1 (позже)
                                                   └──► notifications.dlq.v1 (позже)
```

Это поможет увидеть роли producer, topic, partition, consumer group и брокера в
одном знакомом процессе. Разделим запрос на отправку, попытку доставки и её
результат. На границе с базой данных отдельно разберём, почему сохранение
уведомления и публикация в Kafka не становятся одной атомарной операцией
автоматически. Внешний провайдер доставки также не входит в Kafka-транзакцию.

## Как будем проходить главы

Каждая глава будет состоять из короткой теории, объяснения, небольшого упражнения
и разбора опасных случаев. Конфигурацию Compose для стенда ты напишешь сам по
постепенно выданным требованиям; я разберу её до запуска. Kafka запускаешь ты.
Сначала будем работать с брокером через встроенные CLI-команды, потом добавим
Go-клиент. Так связь между настройкой кластера, его состоянием и кодом будет видна.

Для локального брокера возьмём официальный JVM-based image `apache/kafka:4.4.0`
и Docker Compose, без своего Dockerfile: Compose задаёт запуск и конфигурацию уже
готового образа, а собственный Dockerfile понадобится только если потребуется
собирать изменённый образ. Для Go возьмём `franz-go`: это Kafka-клиент на чистом
Go, с consumer groups, producer idempotence, transactions и администрированием. Локальный
одноброкерный KRaft-узел нужен для повторения команд и сценариев; поведение
HA-кластера разберём отдельно.

## Опасные места, которые будем проверять руками

- **Offset не удаляет сообщение.** Сообщения остаются до конца retention; разные
  группы могут читать один topic независимо и с разных позиций.
- **Неиспользуемый topic сам по себе не исчезает.** Записи в нём удаляются или
  компактизируются по настроенной политике хранения; сам topic удаляют отдельно.
  Для обычной политики `delete` брокер удаляет старые log segments по сроку или
  размеру, даже если consumer давно не запускался.
- **Partition — не map по key.** Key обычно помогает producer выбрать partition;
  одна partition содержит последовательность записей для многих key. Kafka не
  строит индекс, по которому можно мгновенно получить все события одного key.
- **Offset похож на номер позиции, но не на адрес в памяти.** Он задаёт позицию
  в конкретной partition; после compaction или транзакционной записи значения
  offsets могут перескакивать.
- **Commit раньше обработки может потерять работу.** Commit после обработки
  допускает повтор, если приложение упало между эффектом и commit.
- **Повтор — часть нормальной модели.** Producer timeout не всегда говорит,
  принял ли broker запись; consumer может повторно получить уже обработанную запись.
- **Порядок ограничен partition.** Параллельная обработка внутри одной partition
  может нарушить порядок даже при корректной последовательности чтения.
- **Retry может остановить прогресс.** Одна постоянно падающая запись способна
  блокировать обработку последующих записей partition.
- **Kafka не делает распределённую транзакцию с произвольной БД.** Kafka
  idempotence/transactions закрывают определённые границы внутри Kafka, но не
  превращают внешний HTTP-вызов или SQL commit в атомарную часть Kafka-транзакции.
- **Больше consumers не всегда быстрее.** В одной группе число одновременно
  работающих участников ограничено числом назначенных им partitions.
- **Локальный стенд не доказывает отказоустойчивость.** Один broker не показывает
  поведение репликации, ISR и failover как в кластере с несколькими brokers.
